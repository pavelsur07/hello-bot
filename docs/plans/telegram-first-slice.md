# Первый сквозной сценарий Telegram — план реализации

> Для исполнителя: реализуйте задачи по порядку. Для сложной задачи требуется
> независимое ревью в отдельной сессии согласно `AGENTS.md`.

**Цель:** принять текстовое сообщение Telegram, найти ответ в опубликованном
Markdown-разделе, отправить текст со ссылкой на источник и корректно обработать
повторное событие или отсутствие знания.

**Архитектура:** один процесс получает Telegram updates через long polling.
Адаптер переводит update во внутренний `InboundMessage`; сценарий ищет по
Markdown, формирует `OutboundMessage` и отправляет его через адаптер. SQLite
хранит статусы входящих событий для этого первого однопроцессного сценария.
Переход на PostgreSQL остаётся за контрактом `EventStore`.

**Стек:** Python 3.12+, стандартная библиотека (`asyncio`, `json`, `re`,
`sqlite3`, `urllib.request`, `unittest`), без обязательных сервисов и ключей
для тестов и демо.

**Основание:** `docs/architecture.md`, `docs/development.md`,
`KNOWLEDGE_RULES.md`, `AGENTS.md`.

## Границы первого сценария

- Только личные текстовые сообщения Telegram. Фото, вложения, группы и другие
  update-типы пропускаются с продвижением offset.
- Поиск выполняется локально по опубликованным Markdown-разделам без Jev,
  OpenAI, Kimi, фонового worker и векторной БД. Это первый вертикальный срез;
  классификация и генерация добавляются после него.
- На найденный вопрос бот возвращает текст лучшего раздела и строку источника
  вида `Источник: <title> — <section_title>`. В `OutboundMessage.source_refs`
  сохраняется `<source_path>::<section_title>`, где путь относителен корню
  репозитория и записан с `/` на Windows и других ОС.
- Если совпадения нет, ответ ровно: `Не нашёл подтверждённого ответа в базе
  знаний. Уточните вопрос или обратитесь к оператору.`
- Демо запускается только с явным `--knowledge-dir examples/knowledge`.
  Рабочий режим по умолчанию читает `knowledge/`.

## Инварианты и ограничения

- Исходные `.md` файлы остаются источником истины; начальный индекс в памяти
  пересоздаётся при запуске. SQLite содержит только статусы событий.
- Уникальность события — `(channel, external_event_id)`; в этом сценарии
  `channel=telegram`, `external_event_id=str(update_id)`.
- `getUpdates(offset=N)` подтверждает Telegram все updates с ID меньше N.
  Продвигайте offset только после успешной отправки, уже завершённого события
  или осознанного пропуска неподдерживаемого события. При ошибке отправки
  не подтверждайте текущее событие и повторите его позже. Обрабатывайте batch
  по возрастанию `update_id`; после первой ошибки не обрабатывайте и не
  подтверждайте следующие события этого batch.
- SQLite хранит `pending` и `sent`: `claim` атомарно вставляет `pending`,
  `mark_sent` помечает успешную отправку, `release` снимает claim после
  ошибки отправки. Если отправка успешна, а `mark_sent` не сработал, процесс
  останавливается без `release`; следующее событие не подтверждается.
  При старте одного процесса оставшиеся `pending` возвращаются
  в обработку. Разрыв между успешным `sendMessage` и `mark_sent` при аварийном
  завершении может дать второй ответ; Telegram `sendMessage` не предоставляет
  ключ идемпотентности. Укажите это ограничение в документации запуска.
- Не запускайте два экземпляра polling-бота на одном токене и файле SQLite.
  Webhook и распределённая обработка относятся к следующему этапу.
- Если раздел вместе с источником длиннее 3 500 символов, отправьте короткий
  ответ с направлением к оператору и сохраните `source_refs`; не блокируйте
  текущий и следующие updates.

## Данные, уже подготовленные для реализации

- `examples/knowledge/delivery.md`, `pricing.md`: опубликованные вымышленные
  сведения; `internal-draft.md`: черновик, который нельзя выдавать клиенту.
- `examples/demo_update.json`: одно синтетическое Telegram-сообщение для
  локального запуска без сети и токена.
- `examples/demo-dialogs.md`: четыре пользовательских сценария и ожидания.
- `tests/fixtures/telegram_updates.json`: валидное сообщение, неизвестный
  вопрос, нетекстовое сообщение и вопрос с одним общим словом, которому
  нельзя приписать ответ. Повторная доставка проверяется повторной передачей
  первого update, без второго почти одинакового fixture.

## Фокус независимого ревью

Рецензент должен отдельно проверить: черновик не попадает в ответ; повтор не
отправляет второй ответ; ошибка отправки не теряет update; нетекстовое
событие не останавливает polling; пустая рабочая база и вопрос с одним общим
словом не дают боту выдумать ответ. Тесты для них указаны в задачах ниже.

Реальный ответ Telegram дополнительно проверяется вручную с тестовым ботом
и токеном в локальном окружении. Без токена автоматическая приёмка остаётся
полной для логики, но внешний API не считается проверенным.
