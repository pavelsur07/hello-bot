# Архитектура stage 1

## Назначение

Система принимает клиентские сообщения из веб-чата, Telegram и MAX,
определяет тему (`sales`, `support`, `other`) и готовит ответ с опорой на
опубликованные Markdown-файлы. Jev используется для структурированных решений;
модели генерации текста (OpenAI, Kimi) используются для ответов.

## Поток обработки

1. Адаптер канала проверяет событие и создаёт `InboundMessage`.
2. Хранилище проверяет пару `(channel, external_event_id)` на повтор.
3. Явная команда обрабатывается правилом; прочий текст классифицируется Jev.
4. При низкой уверенности сценарий запрашивает уточнение или передаёт диалог оператору.
5. Сценарий ищет разделы опубликованных Markdown-файлов и передаёт их генератору.
6. Ответ содержит ссылки на использованные разделы; адаптер отправляет его в канал.

Порог уверенности и правила передачи оператору определяются на реальных примерах
обращений до включения автоматической маршрутизации.

## Границы

- `core` содержит типы, не зависящие от платформ и поставщиков моделей.
- `channels` знает форматы входящих событий и отправку сообщений.
- `routing` знает категории обращений и результат классификации.
- `conversations` выбирает следующий шаг диалога и использует контракты остальных модулей.
- `knowledge` читает Markdown, строит производный индекс и возвращает фрагменты с источниками.
- `ai` содержит отдельные контракты для решения и генерации текста. Jev не используется как генератор.
- `storage` сохраняет диалоги, состояния и задания. В первом однопроцессном
  сценарии допустим SQLite для статуса входящих событий; PostgreSQL остаётся
  целевым хранилищем при расширении сценариев и нагрузки.

Сценарии не импортируют SDK моделей и код конкретного канала. Инфраструктурные
адаптеры зависят от контрактов, а контракты не зависят от адаптеров.

## Markdown

Исходные `.md` файлы — источник истины. Для каждого раздела индекс сохраняет
`document_id`, путь файла, заголовок раздела, хеш содержимого, область применения
и статус. Переиндексация обновляет изменённые разделы и удаляет устаревшие.
Начальный поиск можно сделать средствами PostgreSQL; векторный индекс добавляется
после проверки качества поиска на реальных вопросах.

## Идентификаторы и данные

Внешний пользователь определяется парой `(channel, external_user_id)`.
Сквозное объединение пользователей разных каналов требует отдельного
подтверждения личности. Сырые сообщения и персональные данные хранятся
только в необходимом объёме; секреты задаются через окружение.

## Порядок реализации

1. Один канал и сквозной сценарий приёма и ответа, затем остальные адаптеры.
2. Загрузка Markdown, поиск и ответы со ссылками на источники.
3. Классификация Jev с набором проверочных обращений.
4. Переключение генератора OpenAI/Kimi по конфигурации задачи.
5. Фоновая переиндексация и наблюдаемость: ошибки, задержка, стоимость вызовов.

Микросервисы, отдельная векторная БД и универсальный движок агентов в stage 1
не требуются.
