# Правила разработки

## Зависимости

1. `core` не импортирует другие модули проекта.
2. `conversations` использует контракты `routing`, `knowledge`, `ai` и `storage`.
3. Код Telegram, MAX, веб-чата, PostgreSQL и SDK моделей остаётся в адаптерах.
4. Не создавайте общий «универсальный AI-клиент»: решение Jev и генерация текста
   имеют разные контракты и разные случаи ошибок.

## Изменения

- Новая модель: добавьте адаптер к нужному контракту, затем проверьте его на
  сохранённом наборе реальных обращений.
- Новый канал: преобразуйте его событие в `InboundMessage` и реализуйте отправку
  `OutboundMessage`. Логику сценариев не меняйте без нового требования.
- Новое знание: добавьте `.md` в `knowledge/` с постоянным `id`, областью и статусом.
  Индекс можно пересоздать из файлов.
- Новое правило маршрутизации: сначала добавьте пример входного сообщения и
  ожидаемой категории, затем меняйте правило или настройки классификатора.

## Надёжность

- Проверяйте подпись или секрет входящего вебхука до разбора события.
- Атомарно отмечайте `(channel, external_event_id)` до запуска сценария.
- Задавайте таймауты внешним API; повторяйте только безопасные операции.
- Не выводите ключи и полные тексты клиентских сообщений в технические логи.
- Для ответа по знаниям сохраняйте использованные `document_id` и разделы.
- При неуверенной классификации предусмотрите уточнение или передачу оператору.

## Избегаем преждевременной сложности

Для первого однопроцессного сценария допускается SQLite как локальное
хранилище статусов входящих событий. При расширении сценариев и нагрузки
целевым хранилищем будет PostgreSQL. Выделяйте сервис или добавляйте
специальное хранилище только после измерения конкретного ограничения.
