# Правила разработки

## Среда и команды

Создайте .venv и установите requirements-dev.txt, затем
python -m pip install --no-build-isolation --no-deps -e .
Используйте Python из .venv; команды установки и демо приведены в README.

Локально и в CI итоговая проверка одна: python scripts/check.py.
Последовательность: Ruff format --check → Ruff check → mypy → unittest →
sdist/wheel → установка wheel и демо без исходного PYTHONPATH.
Сценарий задаёт корень проекта для подпроцессов.

| Задача | Команда в .venv |
| --- | --- |
| Исправить формат | python -m ruff format . |
| Линтер | python -m ruff check . |
| Типы | python -m mypy |
| Все тесты | python -m unittest discover -s tests -v |
| Один сценарий | python -m unittest tests.test_telegram_flow -v |
| Сборка для просмотра | python -m build --no-isolation |
| Все обязательные проверки | python scripts/check.py |

Правила Ruff/mypy — в pyproject.toml. Runtime-код и scripts имеют строгую
типизацию; тестовые функции могут не иметь аннотаций, но их тела проверяются.
Any допустим на границе внешнего JSON/тестовых данных после валидации;
не распространяйте его на предметные контракты.

## Зависимости

Таблица импортов — в architecture.md, контроль — tests/test_architecture.py.
core не зависит от инфраструктуры; сценарии используют contracts/models.
apps связывает реализации. Jev и генераторы остаются разными контрактами.

Новые зависимости, смена архитектуры и разрушительные действия согласуются
до выполнения. Requirements фиксирует версии инструментов и транзитивных
зависимостей; обновление проводится отдельной проверяемой задачей.
Runtime dependencies пуст. CI не публикует пакеты и не запускает живой бот.

## Поведение и данные

Проверяйте результат, ошибки и состояние доставки; не сравнивайте строки
исходников с реализацией. Внешние вызовы заменяются fake-адаптером или opener;
обычным тестам запрещены сеть и живые ключи. tests/fixtures/ и examples/
содержат вымышленные данные, отдельно от knowledge/. Набор классификации
не считается проверкой Jev до его подключения.

Сначала воспроизведите сбой, затем исправьте и повторите затронутые проверки.
После изменения нескольких модулей выполните полный check. Не повторяйте
полный прогон без новых изменений или нерешённого риска.

## Надёжность

- Идемпотентность — пара (channel, external_event_id).
- Неизвестная отправка сохраняет pending и останавливает процесс.
- Pending при старте требует сверки; recover_pending не вызывается автоматически.
- Перед восстановлением остановите бот и согласуйте изменения статусов.
  Для каждого события используйте mark_sent при подтверждённой доставке
  либо release при подтверждённом отсутствии отправки. Не сбрасывайте sent.
- Не выводите токены, URL с токеном и полные сообщения в логи и отчёты.
- Подлинность будущих вебхуков проверяется до разбора.
- Для текущего индекса изменение знаний требует рестарта.

## Завершение

План сложной задачи — в docs/plans/; содержит этапы, результаты команд,
решения и ограничения. Проверьте diff, выполните независимое ревью с чистым
контекстом по AGENTS.md, исправьте существенные замечания и повторите
затронутые проверки. Отчёт отличает подтверждённые локальные результаты
от ещё не выполненных CI и проверки живого API.
