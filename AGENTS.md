# Правила для агентов

Действуют для всего репозитория. Прямые указания пользователя имеют приоритет.
Работайте автономно до проверяемого результата; задавайте вопрос, только когда
без ответа нельзя выбрать корректное поведение или требуется разрешение на
необратимое действие.

## Контекст проекта

- Это модульный монолит на Python 3.12+; назначение и границы модулей описаны
  в `docs/architecture.md` и `docs/development.md`. Текущий MVP и исключения —
  в `docs/mvp.md`; наличие контракта не означает готовую интеграцию.
- Клиентские каналы: веб-чат, Telegram, MAX. Каждый адаптер приводит событие к
  `InboundMessage` и отправляет `OutboundMessage`.
- Источник знаний — опубликованные файлы `knowledge/**/*.md`. Индекс производен
  от файлов и должен быть пересоздаваемым. Правила оформления находятся в
  `KNOWLEDGE_RULES.md`; учебные статьи — только в `examples/knowledge/`.
- Jev принимает структурированные решения, включая классификацию обращений.
  OpenAI и Kimi генерируют текст. Не смешивайте эти возможности в одном API.
- `core` не зависит от инфраструктуры. Сценарии используют контракты; SDK,
  вебхуки и SQL остаются в адаптерах.

## Порядок автономной работы

1. Прочитайте относящиеся к задаче файлы, проверьте состояние рабочего дерева
   и существующие соглашения. Не перезаписывайте чужие изменения.
2. Кратко сформулируйте цель, критерий готовности и затрагиваемые границы.
   Для сложной задачи запишите короткий план с этапами и проверками в
   `docs/plans/<тема>.md`; обновляйте его, если решение меняется. Для простой
   правки отдельный документ не нужен.
3. Реализуйте минимальный сквозной результат. Не добавляйте заранее
   микросервисы, универсальный AI-клиент, отдельную векторную БД или новые
   зависимости без конкретной потребности.
4. Добавляйте проверки, которые ловят реальный сбой поведения. Для внешних
   API используйте тестовые адаптеры; живые ключи и сеть не должны требоваться
   для обычных тестов. Не пишите тесты, лишь повторяющие строки реализации.
5. Запустите относящиеся к изменению тесты и статические проверки. Проверьте
   фактический вывод команд. Если среда не позволяет запустить проверку,
   укажите точную причину и оставшийся риск; не называйте её пройденной.
   Для сложной задачи обязательна единая команда `python scripts/check.py`
   Python из `.venv`. CI использует ту же команду. Установка среды — в README.
6. Проверьте diff на лишние файлы, секреты, изменение публичных контрактов,
   обработку ошибок и соответствие документации. Исправьте найденное.
7. Для сложной задачи проведите независимое ревью по правилу ниже, затем
   исправьте существенные замечания и повторите затронутые проверки.
8. В отчёте перечислите результат, команды и исход проверок, ограничения и
   статус независимого ревью. Не объявляйте работу завершённой без оснований.

## Когда задача сложная

Считайте задачу сложной, если выполняется хотя бы одно условие:

- меняется взаимодействие двух и более модулей или публичный контракт;
- добавляется канал, модель, интеграция или сквозной пользовательский сценарий;
- меняется схема хранения, миграция, индекс знаний или маршрутизация сообщений;
- затронуты аутентификация вебхука, персональные данные, платежи или иная
  критичная обработка;
- работа требует нескольких самостоятельных этапов или заметного рефакторинга.

Документационная правка, локальное переименование или небольшой исправленный
обработчик без этих признаков могут проходить без отдельного ревью.

## Обязательное ревью сложной задачи в отдельной сессии

- После реализации и собственных проверок запустите **отдельную сессию**
  рецензента с чистым контекстом: новую сессию Codex или отдельного агента,
  если среда поддерживает независимые сессии. Рецензент не должен быть
  продолжением сессии автора.
- Передайте рецензенту исходную задачу и критерии готовности, путь к плану,
  список изменённых файлов или diff, команды проверок и их результаты.
  Попросите читать код и искать ошибки, регрессии, нарушения границ модулей,
  проблемы с данными и недостающие проверки. Рецензент даёт замечания с
  серьёзностью и точными ссылками на файлы; он не исправляет код за автора.
- Автор разбирает каждое существенное замечание, исправляет подтверждённые
  проблемы и повторяет затронутые проверки. Если исправление существенно
  меняет решение, передайте обновлённый diff на повторное независимое ревью.
- Самопроверка, повторный запрос в той же сессии и автоматические тесты не
  заменяют это ревью. Если отдельную сессию запустить невозможно, явно
  укажите статус «независимое ревью не выполнено», подготовьте краткую
  инструкцию для следующей сессии и не заявляйте, что сложная задача полностью
  завершена.

## Предметные инварианты

- Повторное входящее событие определяется парой
  `(channel, external_event_id)`; обработка должна быть идемпотентной.
- Вебхук проверяется до разбора и обработки сообщения.
- Пользователь идентифицируется парой `(channel, external_user_id)`;
  объединение между каналами требует подтверждённой идентичности.
- В ответах по знаниям сохраняйте ссылки на исходный Markdown-файл и раздел.
  Непубликованные материалы не участвуют в поиске.
- Не пишите секреты и полные клиентские сообщения в код, тестовые фикстуры
  или технические логи. Внешним вызовам задавайте таймауты; повторяйте только
  безопасные операции.
- При низкой уверенности классификации предусмотрите уточнение или передачу
  человеку. Качество модели проверяйте на сохранённом наборе обращений до
  смены модели или порога.

## Границы автономности и сохранность

- До правок выполните `git status --short --branch` и прочитайте относящиеся
  файлы. Чужие изменения не очищайте, не переносите и не включайте в свой
  коммит без проверки их назначения. Работайте в отдельной ветке; не создавайте
  пустые изменения ради PR. Не переписывайте историю общей ветки.
- Автономно читайте, редактируйте в рамках задачи, запускайте локальные проверки
  и исправляйте подтверждённые ошибки. Согласовывайте смену архитектуры, новые
  зависимости и разрушительные действия. Push, merge, публикация и обращение
  к живым клиентам требуют явного указания пользователя в текущем контексте.
- Не расширяйте MVP новыми каналами, моделями или бизнес-функциями ради тестов.
  Нереализованную возможность укажите как ограничение, а не имитируйте её
  успешную проверку. Низкая confidence не превращается автоматически в other.
- Не открывайте и не печатайте `.env`, живые ключи, credential-хранилища,
  клиентские БД и переписку без конкретной необходимости. Не вставляйте секреты
  в команды, описание PR, diff или ревью. `.env.example` содержит только имена
  действующих настроек; `.env` не загружается автоматически.
- `pending` не сбрасывайте автоматически: неизвестный исход отправки требует
  ручной сверки и согласованного восстановления. Не удаляйте БД ради рестарта.
- Прогресс сложной задачи фиксируйте в `docs/plans/`: выполненные этапы,
  изменения решения, согласования, команды с результатами и ограничения.
  После прерывания продолжайте с первого незавершённого этапа.

## Команды и критерий завершения

Все команды выполняются из корня Python из `.venv`:

```text
python -m ruff format .
python -m ruff check .
python -m mypy
python -m unittest discover -s tests -v
python scripts/check.py
```

Не отключайте проверки и не добавляйте ignore только ради зелёного результата.
Ruff/mypy настроены в `pyproject.toml`; инструменты фиксированы в
`requirements-dev.txt`. Импорты проверяет `tests/test_architecture.py`.
Тестовые данные синтетические, в `tests/fixtures/` и `examples/`.

Завершение требует подтверждённого результата, актуальной документации,
проверенного diff без секретов, успешных относящихся к задаче проверок и
независимого ревью для сложной задачи. В отчёте указывайте ветку, результат
проверок, ревью и нерешённые вопросы. Локальный прогон не равен выполненному
CI или проверке живого API. Не повторяйте проверки без новых изменений,
сбоев или нерешённого риска.
